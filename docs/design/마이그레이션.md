# 마이그레이션 항목 쓰는 법

엔진을 고쳤는데 이미 등록된 프로젝트의 파일 형식도 함께 바꿔야 한다면 마이그레이션 항목을 하나
더한다. 이 문서는 항목 파일 하나와 그 테스트를 쓰는 순서를 안내한다. 값의 정본은 `docs/DESIGN.md`의
P505 절이고, 이 문서와 어긋나면 P505를 따른다.

새 프로젝트에만 필요한 파일은 `scaffold.ts`에서 만든다. `CORE*.md`를 맞추는 일은
`mirrorCore`가 이미 하므로 항목으로 만들지 않는다.

## 1. 파일 하나를 만든다

`migrations/NNNN_<slug>.py`를 엔진 저장소 루트의 `migrations/` 폴더에 둔다. `NNNN`은 0001부터 네 자리
번호이고, 러너는 이 번호 오름차순으로 적용한다. 지금 있는 가장 큰 번호에 1을 더해 쓴다. 번호가 다른
파일과 겹치거나 `ID`가 파일 이름과 맞지 않으면 러너가 rc 2로 거절한다.

엔진의 의존성 0 약속은 항목에도 걸린다. python3 표준 라이브러리만 쓴다.

모양은 예시 항목 `migrations/0001_migrations_readme.py`와 같다. 이 항목은 큐 루트에
`migrations/README.md`를 두고, 같은 본문이 이미 있으면 아무것도 쓰지 않는다. 아래 뼈대는 그 항목을
본뜬 것이다.

```python
import os

ID = "0002-example"
DESC = "큐 루트에 example.txt를 둔다"
DESC_EN = "Put example.txt in the queue root"
SCOPE = "project"
ROLLOUT = "all"
REVERSIBLE = True

BODY = "hello\n"


def _path(ctx):
    return os.path.join(ctx.root, "example.txt")


def targets(ctx):
    return [_path(ctx)]


def apply(ctx):
    p = _path(ctx)
    if os.path.exists(p) and open(p, encoding="utf-8").read() == BODY:
        return
    with open(p, "w", encoding="utf-8") as f:
        f.write(BODY)
    ctx.log("example.txt written")


def verify(ctx):
    assert open(_path(ctx), encoding="utf-8").read() == BODY
```

`DESC`와 `DESC_EN`은 오버레이와 `list`에 한 줄로 그대로 뜬다. 사람이 "지금 무엇을 바꾸는 중인가"를
읽는 유일한 문장이므로 동사로 짧게 쓴다.

`ctx`가 주는 값은 여섯이다.

| 이름 | 값 |
|---|---|
| `ctx.root` | 큐 루트(`.dira`). machine 항목이면 `None` |
| `ctx.project_dir` | 큐 루트의 부모. machine 항목이면 `None` |
| `ctx.project_id` | 레지스트리 id |
| `ctx.local` | `$TICKET_LOCAL`, 없으면 `~/.config/dira` |
| `ctx.engine` | `migrate.py`가 있는 디렉터리 |
| `ctx.log(text)` | 그 프로젝트의 `migrate.log`에 한 줄을 남긴다 |

경로는 모두 `ctx`에서 만든다. `~/Projects/...`처럼 이 머신에서만 맞는 경로를 코드에 적지 않는다.

## 2. `targets`부터 적는다

`apply`를 쓰기 전에 `targets(ctx)`를 먼저 쓴다. 이 항목이 만들거나 고치거나 지울 수 있는 파일을
절대경로로 하나도 빠짐없이 돌려준다. 러너는 이 목록만 보고 백업을 뜨며 `dry-run`도 이 목록만 보여 준다.
목록에 없는 파일을 `apply`가 바꾸면 실패했을 때 그 파일은 되돌아가지 않는다. P505는 이것을 항목의
버그로 규정한다.

빠뜨리기 쉬운 경우가 셋이다.

- 새로 만드는 파일. 아직 없는 파일도 목록에 넣는다. 러너는 없던 파일을 `manifest.json`의
  `absent`에 적어 두었다가, 복원할 때 지운다. 목록에서 빠지면 실패한 뒤에도 반쯤 쓴 새 파일이 남는다.
- 지우거나 이름을 바꾸는 파일. 옛 이름과 새 이름을 둘 다 넣는다.
- 조건에 따라 바뀌는 파일. `apply`가 어떤 분기에서만 건드리는 파일도 넣는다. `targets`는 "이번에
  바뀔 파일"이 아니라 "바뀔 수 있는 파일"이다.

목록이 맞는지는 테스트에서 확인한다(6절). 적용 전후로 바뀐 파일을 모아 `targets`와 비교하면 된다.

항목이 온톨로지 파일을 바꾸면 그 항목이 action-log 한 줄을 직접 쓴다. 러너는 action-log를 쓰지
않는다. 그 action-log 파일도 `targets`에 넣는다.

## 3. `apply`는 멱등으로 쓴다

`apply`는 이미 적용된 상태에서 다시 불러도 결과 파일이 같아야 한다. 러너가 같은 항목을 두 번 부르는
경우가 실제로 있다.

- 러너가 적용 도중에 죽으면 다음 러너가 진행 표식(`migrations/inflight.json`)을 보고 백업으로 되돌린
  뒤 다시 적용한다. 백업이나 복원이 일부만 됐다면 `apply`는 반쯤 바뀐 파일을 만날 수 있다.
- 사람이 오버레이에서 `다시 시도`를 누르거나 `applied.json`을 지우고 다시 돌린다.

그래서 `apply`는 "지금 상태를 보고, 목표 상태와 다를 때만 쓴다"로 짠다. 뼈대의 `apply`가 본문을 먼저
비교하는 이유가 이것이다. 파일 끝에 줄을 덧붙이거나 숫자를 하나 올리는 식의 코드는 두 번 돌면 결과가
달라지므로 쓰지 않는다. 덧붙여야 한다면 그 줄이 이미 있는지 먼저 본다.

`apply`가 예외를 올리면 실패로 처리된다. 처리할 수 없는 상태를 만나면 조용히 넘기지 말고 예외를
올린다.

## 4. `verify`는 결과만 본다

`verify(ctx)`는 `apply`가 끝난 뒤 파일이 목표 상태인지 검사한다. 예외를 올리면(`AssertionError` 포함)
실패다. `apply`의 코드를 다시 부르지 말고 결과 파일을 직접 읽어서 확인한다. 같은 코드로 확인하면 같은
실수를 놓친다.

## 5. `SCOPE` - `ROLLOUT` - `REVERSIBLE`을 고른다

| 값 | 고르는 기준 |
|---|---|
| `SCOPE = "project"` | 프로젝트마다 있는 파일(큐 루트 아래)을 바꾼다. 대부분의 항목이 여기다 |
| `SCOPE = "machine"` | 이 컴퓨터에 하나뿐인 파일(`ctx.local` 아래)을 바꾼다. 한 번만 돈다 |
| `ROLLOUT = "all"` | 기본값. 모든 등록 프로젝트에 바로 돈다 |
| `ROLLOUT = "canary"` | 레지스트리 id가 `dira`인 프로젝트에만 먼저 돌고, `promote` 뒤에 나머지에 돈다(8절) |
| `REVERSIBLE = True` | 적용이 끝난 뒤에도 `revert`로 되돌릴 수 있다 |
| `REVERSIBLE = False` | 실패했을 때 자동 복원만 하고 `revert`는 거절한다 |

machine 항목은 신중하게 고른다. machine 항목이 실패하면 프로젝트 항목은 하나도 돌지 않고, 모든
프로젝트가 미적용으로 막힌다. 프로젝트 하나에서 끝나는 변경이면 `project`로 쓴다.

형식이 바뀌어 옛 엔진이 새 파일을 못 읽게 되는 항목은 `canary`로 낸다. canary 기간에는 `dira`만 새
형식이고 나머지 프로젝트는 옛 형식이다. 이 기간에 엔진이 두 형식을 다 읽게 만드는 일은 그 항목을 싣는
에픽이 맡는다.

`revert`는 마지막 백업으로 파일을 되돌린다. 그 사이에 사람이나 세션이 같은 파일을 고쳤다면 그 변경도
사라진다. 되돌리면 그런 손실이 생기는 파일이면 `REVERSIBLE = False`로 둔다.

## 6. `DIRA_MIGRATIONS_DIR`로 테스트한다

러너는 환경변수 `DIRA_MIGRATIONS_DIR`이 있으면 그 폴더의 항목만 읽는다. 없으면 `migrate.py` 옆
`migrations/`를 읽는다. 테스트는 임시 폴더에 새 항목만 복사한 뒤 이 변수로 가리킨다. 함께
`TICKET_LOCAL`도 임시 폴더로 돌려 둔다. 그래야 러너 락(`$LOCAL/run/migrate.lock`), 상태 파일, 승격
파일, machine 기록이 실제 `~/.config/dira`에 쓰이지 않는다.

큐 루트는 임시 폴더에 `.dira`를 하나 만들어 `--root`로 넘긴다. 바꿀 파일의 옛 모양을 그 안에 미리
깔아 둔다. 그다음 아래 다섯 가지를 확인한다.

1. **dry-run은 아무것도 바꾸지 않는다.** `python3 migrate.py dry-run --root R`이 `targets`를 `있음`/`없음`
   표시와 함께 내고, 실행 전후로 `R` 아래 파일이 하나도 바뀌지 않는다.
2. **적용과 검증이 통과한다.** `python3 migrate.py apply --root R`이 rc 0이고 `R/migrations/applied.json`의
   그 항목 `state`가 `ok`다.
3. **두 번 돌려도 같다.** 한 번 더 `apply`하면 rc 0이고 `migrate.log`에 새 `START` 줄이 없다.
   `applied.json`을 지우고 다시 돌려도 `targets` 파일의 sha256이 첫 실행 직후와 같다. 이 둘째
   확인이 3절의 멱등을 검사한다.
4. **`targets`가 빠짐없다.** 적용 전후로 `R` 아래 바뀐 파일을 모은다(`R/migrations/` 아래 기록 -
   백업 - 로그는 뺀다). 그 집합이 `targets(ctx)`에 모두 들어 있어야 한다.
5. **실패하면 되돌아간다.** `verify`가 실패하도록 옛 모양을 일부러 망가뜨린 픽스처로 `apply`를 돌린다.
   rc 1이고, 기록이 `failed`이고, `targets` 파일의 sha256이 적용 전과 같아야 한다.

러너의 공통 동작(락, 진행 표식 복구, 세션 대기, 게이트)은 `test_migrate.py`가 이미 검사한다. 새 항목의
테스트는 그 항목이 만드는 파일만 본다.

## 7. 실패하면 무엇이 되돌려지는가

러너는 항목을 적용하기 직전에 `targets` 중 있던 파일을 원본 그대로
`<루트>/migrations/backup/<id>/<UTC 초>/`에 복사하고, `manifest.json`에 있던 파일(`existed`)과 없던
파일(`absent`)을 적는다. zip이나 tar로 묶지 않고, 백업은 자동으로 지우지 않는다.

| 경우 | 결과 |
|---|---|
| `apply`나 `verify`가 예외를 올림 | `existed`는 백업에서 복사해 되돌리고 `absent`는 지운다. 기록은 `failed`이고 `error`에 예외의 마지막 줄이 남는다. 로그는 `result=restored`다. 그 프로젝트의 다음 항목은 돌지 않고 러너는 다음 프로젝트로 간다 |
| 복원도 실패함 | 기록은 `broken`, 로그는 `result=broken`이다. 게이트가 계속 막고 오버레이에 `복원 실패`가 붙는다 |
| 러너가 죽음 | 다음 러너가 `inflight.json`을 보고 그 백업으로 먼저 복원한다 |
| machine 항목이 실패함 | 같은 복원을 하고, 프로젝트 항목은 하나도 돌지 않는다 |
| 백업 자체가 실패함 | 적용하지 않고 `failed`로 기록한다 |

되돌아가는 것은 `targets`에 적은 파일뿐이다. 2절을 빠뜨리면 이 표가 지켜지지 않는다.

기록이 `ok`가 아닌 동안 `migrate.py gate <루트>`가 rc 1을 내고, 그 프로젝트의 워커는 claim하지 않는다.
`runner.log`에는 `SKIP 마이그레이션 미적용 <id>` 줄이 남는다.

## 8. canary 뒤 `promote`

`ROLLOUT = "canary"` 항목은 이렇게 나간다.

1. 항목을 커밋하고 push한다. 앱이 재기동하거나 화면이 새 항목을 잡으면 러너가 `dira` 프로젝트에만
   적용한다. 다른 프로젝트는 그 항목에 대해 보류 상태이고, 보류는 디스패치를 막지 않는다.
2. QA가 `dira` 프로젝트에서 그 항목을 검증한다.
3. QA가 통과시키면 `python3 migrate.py promote <id>`를 돌린다. `$LOCAL/migrations/promoted/<id>` 빈
   파일이 생긴다.
4. 그 뒤 `python3 migrate.py check --all`이 나머지 프로젝트를 미적용으로 낸다. 다음 러너가 그
   프로젝트들에 적용한다.

승격 파일은 기계마다 따로 있다. 원격 기계에서도 승격하려면 그 기계에서 `promote`를 따로 돌린다.

## 9. 번들에는 따로 할 일이 없다

앱 번들은 `migrations/` 폴더를 통째로 싣는다. 새 항목 파일을 `package.json`의 `extraResources`나 `dist`
존재 검사에 하나씩 더하지 않아도 된다. 파일을 폴더에 넣고 커밋하면 끝이다.

## 넘기기 전에

- [ ] 파일 이름의 번호가 겹치지 않고 `ID`가 파일 이름과 같다.
- [ ] `targets`에 새로 만드는 파일과 지우는 파일이 들어 있다.
- [ ] `apply`를 두 번 불러도 결과가 같다.
- [ ] `verify`가 `apply` 코드를 다시 쓰지 않고 결과 파일을 읽는다.
- [ ] 6절의 다섯 가지 확인이 테스트에 있다.
- [ ] 형식이 바뀌는 항목이면 `ROLLOUT = "canary"`이고, 승격은 QA 티켓의 일로 넘겼다.
