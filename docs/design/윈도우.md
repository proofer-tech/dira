# 기획서 - dira Windows 버전 (요구 `bf03521c`, 에픽 P524)

작성 2026-10-26, pm. 이 문서는 기획서이고 코드 패치는 포함하지 않는다. 로드맵 행과 수용조건의 정본은
`docs/DESIGN.md` §P524이고, 이 문서는 그 근거와 설계를 담는다.

## 1. 목표

사람 문장: *"지금 맥에서 하는 경험처럼 exe만 실행시키면 동작하면 좋겠어요"*.

- **성공의 정의**: 깨끗한 Windows 11 x64 PC에서 사람이 설치 파일(exe) 하나를 내려받아 실행한다. 관리자 권한 창(UAC)과
  재부팅이 없다. 사람이 직접 하는 일은 Claude 로그인 한 번뿐이다. 그 뒤 맥과 같이 프로젝트를 등록하고, 티켓을 발행하면 워커가
  티켓을 집어 `.done`까지 처리한다.
- **WSL은 쓰지 않는다.** WSL 2는 Windows 11에도 기능만 들어 있고 배포판 설치와 가상화 켜기에 관리자 권한과 재부팅이
  필요하다. 위 정의와 맞지 않는다.
- **맥은 회귀하지 않는다.** Windows 작업이 바꾸는 모든 엔진 코드는 맥에서도 같은 코드로 돈다. 맥 전용 분기와 Windows 전용
  분기는 플랫폼 계층 한 곳에만 둔다.

## 2. 현재 상태 - 맥 전용인 지점 (실측 2026-10-26)

| 외부 도구 | 사용자 PC에 `claude`, `git`, `python3`가 이미 있다고 가정한다 | 설치 경험 전체 |

**Claude Code의 Windows 사실(공식 문서 `code.claude.com/docs/en/setup`, 2026-10-26 확인)**

- 네이티브 Windows 10 1809 이상과 Windows 11을 지원한다. x64와 ARM64 모두 된다.
- 설치는 PowerShell `irm https://claude.ai/install.ps1 | iex`이고 **관리자 권한이 필요 없다.** 실행 파일은
  `%USERPROFILE%\.local\bin\claude.exe`에 놓이고 백그라운드에서 스스로 업데이트한다. `winget install Anthropic.ClaudeCode`도
  있다.
- Git for Windows는 선택이다. 있으면 Bash 도구가 Git Bash를 쓰고, 없으면 PowerShell 도구로 대신한다. Git Bash를 못 찾을 때
  경로를 알려 주는 환경변수는 **`CLAUDE_CODE_GIT_BASH_PATH`**이다(예: `C:\Program Files\Git\bin\bash.exe`).
- 네이티브 Windows에서는 샌드박스가 지원되지 않는다.

## 3. 핵심 판단 - Git Bash는 어차피 필요하다

세션은 프로토콜대로 `bash .dira/push.sh ship ...`을 부르고, 큐 훅 다섯 벌(합 2,100여 줄)이 bash다. 세션이 Bash 도구 없이
PowerShell로만 돌면 이 훅을 부를 수 없다. 그래서 **Windows 판에도 Git(Git Bash 포함)은 필수 의존**이고, 앱이 이것을
챙긴다(§5). 이 사실이 두 갈래의 비용을 바꾼다.

| 갈래 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. Git Bash 실행 | 동봉한 Git Bash로 `tick.sh`와 훅을 그대로 돌린다. 안 되는 것(cron, FIFO, 심볼릭 링크, 프로세스 그룹)만 바꾼다 | 첫 exe가 빠르다. 맥과 같은 코드가 돈다 | MSYS의 `kill` - `ps`는 Windows 프로세스 트리를 다 못 본다. 포크가 느려 tick 한 번이 맥보다 길다 |
| B. Python 포팅 | `tick.sh`를 `tick.py`로 옮기고 맥도 그것을 쓴다 | 오래 유지하기 좋다. 프로세스 관리가 정확하다 | 2,769줄 재작성. 맥 회귀 위험이 가장 크다 |

**권장: A로 첫 출시를 하고, B는 그 뒤에 절 단위로 옮긴다.** 홈 대화는 장기적으로 B가 낫다고 했고 이 판단은 유지한다. 다만
훅이 bash라서 B를 해도 Git Bash 의존은 사라지지 않는다. 그렇다면 첫 exe까지의 거리를 줄이는 A가 먼저다. B는 A에서 실측으로
드러난 문제 절(프로세스 감시, reap, 쿨다운)부터 Python으로 옮긴다.

## 4. 설계 - 바꾸는 것

### 4.1 스케줄 - cron -> 작업 스케줄러

- 사용자 단위 `schtasks /create`는 관리자 권한이 필요 없다. 최소 주기가 1분이라 30초 주기는 작업 하나가 `dispatch.py`를
  띄우고 그 안에서 30초 뒤 한 번 더 도는 방식으로 만든다(작업 둘을 30초 어긋나게 거는 방식보다 관리할 대상이 적다).
- 창이 깜박이지 않도록 콘솔 없는 `pythonw.exe`로 띄운다.
- `apps/teams/lib`의 `cronLine` - `cronRegisterCmd`와 `dispatch.py`의 `crontab -l` 판정을 "스케줄 등록부" 인터페이스 하나
  (등록 - 해제 - 조회)로 감싸고 구현을 플랫폼별로 둔다. 맥 구현은 지금의 cron 그대로다.

### 4.2 참견 inbox - FIFO -> 파일 큐

- MSYS의 FIFO는 MSYS 프로세스끼리만 통하고, Node가 `O_NONBLOCK`으로 여는 것은 Windows에서 되지 않는다.
- 권장안은 named pipe가 아니라 **디렉터리 inbox**다. 참견 한 건을 `inbox-<세션>/<시각>-<난수>.txt`로 쓰고 tick이 읽은 뒤
  지운다. 쓰는 쪽은 임시 이름으로 쓰고 rename한다. 맥도 같은 방식으로 바꿀 수 있고, 그러면 플랫폼 분기가 생기지 않는다.
  홈 에이전트 프롬프트에 들어 있는 명령도 같이 바뀐다.

### 4.3 프로세스 관리

- 갈래 A에서는 세션 프로세스를 띄우는 자리만 Python 도우미로 감싼다. 도우미가 Windows Job Object(`ctypes`, 표준
  라이브러리)에 자식을 넣고, 죽일 때는 Job을 닫는다. 맥은 지금처럼 프로세스 그룹을 쓴다.
- 살아 있는지 판정하는 `ps` - `kill -0`은 도우미의 `alive <pid>` 명령으로 바꾼다(Windows는 `OpenProcess`).
- `timeout` 명령은 Git Bash에 coreutils로 들어 있으나 Windows 프로세스 트리를 다 못 죽인다. 세션을 감싸는 `timeout`은
  도우미로 옮긴다.

### 4.4 링크 - 심볼릭 링크 -> 디렉터리 junction

- 워커 워크트리의 `.dira`는 큐 디렉터리를 가리키는 링크다. Windows 심볼릭 링크는 개발자 모드나 관리자 권한이 필요하므로
  디렉터리 junction(`mklink /J`, 권한 불필요)을 쓴다. junction은 같은 PC의 로컬 경로에만 걸린다.

### 4.5 큐 불변 - 그대로 지킨다

- 상태 3종(없음 / `.wip` / `.done`), 해시 파일명, claim 락은 바꾸지 않는다.
- claim은 원자적 하드 링크다. NTFS는 관리자 권한 없이 하드 링크를 지원하므로 `os.link`가 그대로 된다. 이것을 단계 0에서
  가장 먼저 실측한다.
- Windows의 `os.rename`은 대상이 있으면 실패하고, 다른 프로세스가 연 파일은 rename하지 못한다. `.wip`에서 `.done`으로
  바꾸는 rename이 편집기나 GUI 서버가 파일을 연 순간 실패할 수 있다. 엔진과 GUI 서버는 파일을 읽은 즉시 닫고, rename은 짧게
  재시도한다.

### 4.6 데스크톱 셸과 GUI 서버

| 맥 | Windows |
|---|---|
| 독 배지 | 작업 표시줄 오버레이 아이콘(`setOverlayIcon`) |
| 키체인 | 환경변수 저장소(`env-store.ts`)는 이미 Electron `safeStorage`를 쓰고, Windows에서는 DPAPI가 그 백엔드가 된다. 백엔드 판정(`isEncryptionAvailable`) 문구만 Windows에 맞춘다 |
| `/opt/homebrew` PATH 복원 | 없음. 대신 동봉한 Python, Git, claude 경로를 앱이 PATH 앞에 넣는다 |
| `Library/Application Support/dira/engine` | `%APPDATA%\dira\engine`. Electron `app.getPath("userData")`로 고친다 |
| `osascript` 4곳 | 쓰임새별로 Electron API나 PowerShell로 바꾸고, 대체가 없으면 그 기능을 Windows에서 숨긴다 |
| `bash` 19곳 | 동봉한 Git Bash의 절대 경로로 부른다 |

## 5. 설치 경험 - 앱이 의존 도구를 챙긴다

1. **설치 파일**: electron-builder의 NSIS, `perMachine: false`(사용자 단위 설치, `%LOCALAPPDATA%\Programs\dira`). UAC 창이
   뜨지 않는다.
2. **Python**: python.org의 embeddable 배포판(x64, 약 10 MB)을 앱에 동봉한다. 엔진은 표준 라이브러리만 쓰므로 pip이
   필요 없다. 엔진을 부를 때 `PYTHONUTF8=1`을 건다.
3. **Git과 Git Bash**: 첫 실행에 PC에 설치된 Git for Windows를 먼저 찾는다. 없으면 PortableGit(약 60 MB)을
   `%LOCALAPPDATA%\dira\git`에 내려받아 푼다. 앱 설치 파일에 넣지 않는 이유는 크기다.
4. **Claude Code**: `claude.exe`가 없으면 공식 설치 스크립트(`install.ps1`)를 사용자 권한으로 돌린다. 워커 세션 환경에
   `CLAUDE_CODE_GIT_BASH_PATH`를 3번의 `bash.exe` 경로로 건다.
5. **로그인**: 앱이 `claude` 로그인 흐름을 띄우고, 사람은 브라우저에서 한 번 로그인한다. 사람이 하는 일은 이것뿐이다.
6. 첫 실행 화면은 1-5를 단계 표시줄로 보여 주고, 실패한 단계에는 그 자리에서 다시 시도하는 버튼을 둔다.

## 6. Windows 함정과 대응

| 함정 | 대응 |
|---|---|
| 한국어 Windows 기본 인코딩 cp949 | 엔진 실행 환경에 `PYTHONUTF8=1`. 파일은 모두 UTF-8로 읽고 쓴다 |
| git 체크아웃이 CRLF로 바뀜 | 저장소 `.gitattributes`에 `* text=auto eol=lf`, `*.sh`는 `eol=lf` 고정. 워크트리를 만들 때 `core.autocrlf=false` |
| 260자 경로 제한 | `core.longpaths=true`. 워크트리 경로를 짧게 유지한다(`.dira/worktrees/w1` 구조는 이미 짧다). OS의 긴 경로 설정은 관리자 권한이 필요하므로 기대지 않는다 |
| 열린 파일 rename 실패 | §4.5 - 즉시 닫기와 짧은 재시도 |
| 백신 실시간 검사 | 큐 디렉터리의 잦은 rename이 느려질 수 있다. 단계 0에서 Defender 기본 설정으로 tick 한 번의 시간을 잰다 |
| Google Drive 가상 드라이브(G:) | 하드 링크와 junction이 안 될 수 있다. 단계 0에서 확인하고, 안 되면 큐와 워크트리는 로컬 디스크에만 두도록 등록 화면에서 막는다 |
| 서명 안 된 exe | SmartScreen이 "알 수 없는 게시자" 경고를 띄운다. §8의 인증서 조달이 끝나기 전에는 경고를 넘기는 방법을 첫 화면 안내에 적는다 |

## 7. 단계

| 단계 | 내용 | 끝났다고 보는 조건 |
|---|---|---|
| 0. 실측 | Windows 11 VM에 Git for Windows와 embeddable Python을 수동으로 놓고 `tick.sh`를 Git Bash로 돌린다. claim 하드 링크, junction, rename, tick 소요 시간을 잰다 | 실패 목록 한 장. 이 목록이 단계 1의 범위를 확정한다 |
| 1. 엔진 이식(갈래 A) | 스케줄 등록부, 디렉터리 inbox, 프로세스 도우미, junction, POSIX 전용 Python 호출 정리 | VM에서 수동 설치 상태로 티켓 하나가 `.done`까지 간다. 맥 엔진 테스트가 그대로 통과한다 |
| 2. 앱 이식 | GUI 서버의 bash - osascript - crontab 자리, 데스크톱 셸(§4.6), 의존 도구 부트스트랩(§5) | 깨끗한 VM에서 exe 실행 -> 로그인 -> 티켓 하나 `.done` |
| 3. 빌드와 배포 | electron-builder Windows 대상, `dist` 검사 경로를 플랫폼별로, 릴리스 스크립트에 Windows 산출물, 자동 업데이트 | 릴리스 하나에 dmg와 exe가 같이 올라간다 |
| 4. QA와 매뉴얼 | 깨끗한 VM 시나리오 전체, 매뉴얼 Windows 장 | QA 통과, 매뉴얼 게시 |
| 5. Python 포팅(갈래 B) | 단계 0-4에서 문제가 된 tick 절부터 `tick.py`로 옮긴다 | 절마다 따로 정한다 |

단계 0은 다른 모든 단계의 범위를 바꾸므로, 단계 1 이후의 티켓은 단계 0의 결과를 읽고 발행한다.

## 8. 사람이 정할 것 (기획 단계의 미결정)

1. **코드 서명 인증서** - Azure Trusted Signing(월 약 10달러, 개인 및 소규모 사업자 자격 조건 있음)이나 EV 인증서(연 수십만
   원 이상, 하드웨어 토큰). 비용과 법인 정보가 필요하므로 사람이 정한다. 정하기 전에도 단계 0-2는 진행할 수 있다.
2. **지원 범위** - 이 기획은 Windows 11 x64를 1순위로, Windows 10 22H2 x64를 2순위로 둔다. ARM64(Copilot+ PC)는 범위
   밖으로 둔다.
3. **일정 기준** - 대회 데모(온톨로지 `대회-원티드AI챔피언십2026/03_배포데모_설계.md`가 macOS 전용을 가장 큰 위험으로
   꼽았다)에 맞출지에 따라 단계 3까지를 먼저 끝낼지, 단계 5를 앞당길지가 달라진다.
4. **테스트 장비** - Windows 11 VM을 어디에 둘지(이 맥의 UTM이나 Parallels, 클라우드 VM). Apple Silicon 맥의 VM은 ARM64
   Windows라 x64 확인에는 x64 에뮬레이션이나 클라우드 VM이 필요하다.

## 9. 범위 밖

- WSL 경로, 관리자 권한이 필요한 모든 설치 방식
- Linux 데스크톱 판

- 네이티브 Windows 샌드박스(Claude Code가 지원하지 않는다)
