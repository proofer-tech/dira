# 안 돌 때

증상에서 원인으로 내려간다. 처음 마주치는 사람은 "헤드리스 토큰이 만료됐다"가 아니라
"아무 일도 안 일어난다"를 들고 오기 때문이다.

**각 증상은 화면에서 볼 자리가 먼저다.** 앱이 이미 판정해서 그리고 있는 것을 터미널에서 다시
캐낼 이유가 없다. 화면이 답을 안 주는 데까지 갔을 때 로그를 연다.

## 티켓이 보드에 안 보인다

**화면**: 보드에서 필터·검색을 전부 풀고, 테이블 뷰(`?view=table`)로도 본다. 완료 레인은 최근
20건만 그리므로 오래된 완료는 테이블에만 있다. 그래도 없으면 **알림 종**을 연다 — 아무도
집어 가지 않는 `할당됨` 티켓은 레인이 아니라 거기 뜬다.

**원인**: 양쪽 다 없으면 그 파일이 큐 판정을 통과하지 못한 것이다. 셋 중 하나다.

- **`tickets/` 바로 밑이 아니다.** 큐는 평면이라 하위 디렉터리를 보지 않는다. 이 경우 워커가
  `WARN 구 레이아웃에 티켓 n건이 남아 있다`를 남긴다.
- **파일명이 `.md`로 안 끝나거나 `.`으로 시작한다.**
- **이미 `.wip`·`.done` 접미사다.** 그건 열린 티켓이 아니다([티켓이 지나는
  상태](/docs/states)).

```bash
ls <루트>/tickets/                          # 평면인지, 이름이 <해시>.md인지
<루트>/workers/w1.sh list                    # 엔진이 실제로 무엇을 열린 티켓으로 보나
```

`list`에 없고 `ls`에는 있으면 판정에서 빠진 것이다. `WARN` 줄은 `runner.log`에 남는다
([로그 읽는 법](/docs/logs) §`runner.log`).

## 대기인데 아무도 안 집는다

**화면**: 카드에 주황색 **`deps` 태그**가 붙었는지 본다. 붙었으면 선행 티켓이 안 끝난 것이고,
선행이 끝나면 아무도 손대지 않아도 사라진다. 태그가 없으면 **알림 종**을 연다 — `답변을
기다리는 티켓`과 `아무도 집어 가지 않는 티켓`이 거기 각각 자기 건수를 말한다.

**원인**은 종 항목마다 다르다.

- **답변 대기** — 세션이 막혀 `## 질문 n`을 붙이고 스스로 잠갔다. 존재하지 않는 해시가 `deps`로
  걸려 있어 사람이 답을 쓰기 전에는 어떤 워커도 집지 않는다. 티켓 상세의 진행 기록 맨 끝
  입력칸이 그 답을 쓰는 자리다. 같은 티켓이 계속 죽어서 여기 온 경우도 있다 — 자동 회수는
  2회까지고 3회째부터 답변 요청으로 전환한다(세션이 `## 블록`을 남겼으면 횟수와 무관하게 즉시).
- **아무도 집어 가지 않는 티켓(`할당됨`)** — 열린 파일인데 `session_id`가 채워져 있다. 엔진이
  만들지 않는 조합이고, 도달하면 선정에서 영구 제외돼 조용히 죽는다. 종 안의 그 줄에 붙은
  **`할당 해제`** 버튼 하나가 푼다.

```bash
<루트>/workers/w1.sh list                       # deps 대기 / 할당됨이 그대로 찍힌다
tail -20 <루트>/workers/runner.log | grep ASK   # 답변 요청으로 전환된 시점
```

## 워커는 도는데 아무것도 안 한다

**화면**: 헤더 우측의 **설정 버튼**을 본다. 인증이 없으면 그 버튼 자체에 `인증 필요`가
붙는다. **알림 종** 첫 항목도 같은 것을 말한다 — `Claude 인증이 없어 티켓이 디스패치되지
않습니다`. 설정 다이얼로그의 인증 구획에서 그 자리에서 발급한다([인증](/docs/auth)).

**원인**: 헤드리스 토큰이 없거나 만료됐다. 토큰이 아예 없으면 워커는 디스패치 자체를 하지
않는다 — 엔진이 `claude`이고 비대화형(cron)인데 `oauth-token`이 없으면 조용히 `exit 0`하고,
처음 한 번만 로그에 남긴다(`.authwarn` 파일로 중복 로그를 막는다). 토큰이 있지만 만료됐다면
디스패치는 일어나되 세션이 인증 오류로 곧바로 끝나 `FAIL`로 남는다.

```bash
ls -la ~/.config/dira/oauth-token             # 파일이 있는지, 언제 만들었는지
grep 'AUTH 대기' <루트>/workers/runner.log     # 최초 1회만 남는 줄
```

`FAIL`이 찍혀 있다면 이유는 그 줄의 세션 로그에 있다([로그 읽는
법](/docs/logs) §`logs/`).

## 세션이 뜨자마자 죽는다

**화면**: **알림 종**의 `세션이 열리자마자 죽는 워커` 항목이다. 한도 소진·API 과부하·연결 끊김처럼
큐도 워커도 멀쩡한데 세션만 죽는 경우고, 사유 문구에 **복구 시각이 들어 있으면 그대로
보여 준다**(`session limit · resets 7:40pm` 같은 줄).

**원인**: 앱 밖이다. 여기서 할 일은 기다리는 것이거나 한도를 올리는 것이지 큐를 고치는 게
아니다. 그동안 워커는 `idle`↔`running`을 오가고 티켓은 `대기`에 앉아 있어 **화면의 다른 곳은
전부 정상으로 보인다** — 그래서 이 항목이 따로 있다.

**이 알림은 저절로 꺼진다.** 마지막 tick 결과가 10분보다 오래됐거나 다음 tick이 `DONE`이면
사라진다.

**기다리기 싫으면 손으로 지운다.** 항목 오른쪽 아래 `읽음으로 표시`를 누르면 그때 나열돼 있던
실패가 한 번에 덮이고 항목이 통째로 접힌다. 한도가 풀린 걸 이미 아는데 문구가 아직 남아 있을 때
쓰라고 있는 버튼이다. 네 알림 중 이렇게 지울 수 있는 것은 이 항목뿐이다 — 나머지 셋은 사람이
손을 대야 꺼진다.

지운다고 다음 사고까지 묻히지는 않는다. 덮이는 단위가 워커가 아니라 **실패 하나**이고 그 키가
실패의 로그 파일명이라, 새 `FAIL`이 오면 파일명이 달라 항목이 다시 뜬다.

```bash
grep -E 'FAIL|TIMEOUT' <루트>/workers/runner.log | tail -5
```

`FAIL` 줄 꼬리의 로그 파일명이 사유의 원본이다 — 마지막 줄 JSON의 `result`가 그 문구다
([로그 읽는 법](/docs/logs) §`logs/`).

## 워커가 `stale`이다

**화면**: 워커 화면의 상태 칸이다. 행마다 pid가 같이 보인다.

**원인**: 이게 항상 오작동은 아니다. 회수(`reap`) 판정은 시간이 아니라 **프로세스 생존**이다 —
오래 걸리는 정상 세션과 매달린 세션은 걸린 시간만으로 구분되지 않기 때문이다. pid가 살아
있으면 `running`이고 아무리 오래 걸려도 그대로 두고, 죽었으면 `stale`이며 **다음 tick이
회수한다**(디스패치 직후 3분 유예는 있다). `stale`을 봤다면 대개 30초 안에 저절로 풀린다.

```bash
<루트>/workers/w1.sh reap                                 # 지금 한 번 강제로 돌려본다
tail -20 <루트>/workers/runner.log | grep -E 'REAP|SKIP'
```

`REAP`이 찍히면 회수된 것이고, 아무것도 안 찍히면 세션이 아직 살아 있는 것이다 — 그 경우엔
기다리는 것이 맞는 대응이다([로그 읽는 법](/docs/logs) §`runner.log`).

## cron에 등록됐는데 안 깨어난다

**화면**: 워커 화면의 상태 칸이 `stopped`면 crontab에 그 워커의 줄이 없다는 뜻이다(파일만
있다). `idle`이면 등록은 돼 있다.

**원인**: 앱에서 워커를 등록할 때마다 macOS가 **`앱 관리` 권한**을 다시 묻는다 — 앱이
crontab에 줄을 쓰는 동작이라 그렇다. 전체 디스크 접근 권한과는 별개고, **이 승인은 다음
등록까지 남지 않는다.** 응답하기 전까지 등록 자체가 멈춰 있어서, 창을 놓치면 "만들었는데 안
돈다"로 보인다([인증](/docs/auth) §워커를 만들 때 묻는 `앱 관리`).

```bash
crontab -l | grep <워커이름>     # 그 워커의 두 줄이 실제로 등록됐는지
```

안 보이면 `설정 › 개인정보 보호 및 보안 › 앱 관리`에서 승인하고 워커를 다시 만든다. 손으로
거는 절차는 [엔진만으로 돌리기](/docs/cron) §crontab 두 줄에 있다. 등록은 됐는데 로그가
아예 안 자란다면 다음 항이다([로그 읽는 법](/docs/logs) §`cron.log`).

## 워커가 아예 안 뜬다

**화면**: 프로젝트 목록에서 그 프로젝트가 `연결 안 됨`이거나, 워커 화면에 있어야 할 행이 아예
없다. 앱도 그 경로를 못 읽고 있다는 뜻이라, 이건 큐의 문제가 아니라 경로의 문제다.

**원인**: 티켓 루트가 클라우드 마운트(구글드라이브 등)인데 마운트가 안 붙어 있다. 워커 파일
자체가 그 마운트 안에 있으므로, 마운트가 빠지면 cron이 때리는 경로에 실행할 스크립트가 없다 —
에러 없이 조용히 실패한다. "큐가 비어서 안 도는구나"로 오해하기 쉬운 자리다([엔진만으로
돌리기](/docs/cron) §큐를 프로젝트 밖에 둘 때).

```bash
ls <루트>/workers/     # 워커 파일이 실제로 보이는지부터 확인
```

안 보이면 마운트 상태를 먼저 본다. 마운트는 붙어 있고 행도 보이는데 `runner.log`가 자라지
않는다면 셔뱅·실행 권한이 깨진 것이고, 그건 `cron.log`에만 남는다([로그 읽는
법](/docs/logs) §`cron.log`).

다음은 [로그 읽는 법](/docs/logs)이다.
