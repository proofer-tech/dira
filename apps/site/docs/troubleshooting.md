# 트러블슈팅

증상에서 원인으로 내려간다. 처음 마주치는 사람은 "헤드리스 토큰이 만료됐다"가 아니라
"cron이 도는데 아무 일도 안 일어난다"를 들고 오기 때문이다.

## cron이 도는데 아무 일도 안 일어난다

**원인**: 헤드리스 토큰이 없거나 만료됐다. 토큰이 아예 없으면 워커는 디스패치 자체를
하지 않는다 — 엔진이 `claude`이고 비대화형(cron)인데 `oauth-token`이 없으면 조용히
`exit 0`하고, 처음 한 번만 `runner.log`에 남긴다(`.authwarn` 파일로 중복 로그를 막는다).
토큰이 있지만 만료됐다면 디스패치는 일어나되 세션이 인증 오류로 곧바로 끝나 `FAIL`로
남는다.

```bash
tail -20 <루트>/workers/runner.log     # AUTH 대기 / FAIL 줄 확인
ls -la ~/.config/dira/oauth-token      # 파일이 있는지, 언제 만들었는지
```

없거나 오래됐으면 [헤드리스 인증](/docs/auth)대로 다시 발급한다.

## 워커가 아예 안 뜬다

**원인**: 티켓 루트가 클라우드 마운트(구글드라이브 등)인데 마운트가 안 붙어 있다.
워커 파일 자체가 그 마운트 안에 있으므로, 마운트가 빠지면 cron이 때리는 경로에
실행할 스크립트가 없다 — 에러 없이 조용히 실패한다. "큐가 비어서 안 도는구나"로
오해하기 쉬운 자리다([워커 만들기](/docs/worker) 참고).

```bash
ls <루트>/workers/     # 워커 파일이 실제로 보이는지부터 확인
```

안 보이면 마운트 상태를 먼저 본다. `runner.log`조차 갱신되지 않는 것도 같은 증거다.

## 전체 디스크 접근 권한을 줬는데도 안 된다

**원인**: 전체 디스크 접근 권한과 별개로, **데스크톱 앱**에서 `새로 만들기`로 워커를
등록할 때마다 macOS가 `앱 관리` 권한을 다시 묻는다 — 앱이 crontab에 줄을 쓰는 동작이라
그렇다. 이 승인은 다음 등록까지 남지 않는다. 응답하기 전까지 등록 자체가 멈춰 있다
([헤드리스 인증](/docs/auth) §데스크톱 앱에서 워커를 만들 때는 다르다 참고).

```bash
crontab -l | grep <워커이름>     # 그 워커의 두 줄이 실제로 등록됐는지
```

안 보이면 `설정 › 개인정보 보호 및 보안 › 앱 관리`에서 승인하고 워커를 다시 만든다.

## 티켓이 진행중에 멈춰 있다

**원인**: 이게 항상 오작동은 아니다. 스테일 수거(`reap`)는 시간이 아니라 **프로세스
생존**으로 판정한다 — 오래 걸리는 정상 세션과 매달린 세션은 걸린 시간만으로 구분되지
않기 때문이다. 세션이 실제로 죽었으면 다음 tick의 `reap`이 회수하고(디스패치 직후
3분 유예는 있다), 세션이 살아있으면 아무리 오래 걸려도 그대로 둔다.

```bash
<루트>/workers/w1.sh reap    # 스테일 수거를 지금 한 번 강제로 돌려본다
tail -20 <루트>/workers/runner.log | grep -E 'REAP|SKIP'
```

`REAP`이 찍히면 회수된 것이고, 아무 것도 안 찍히면 세션이 아직 살아있는 것이다 —
그 경우엔 기다리는 것이 맞는 대응이다.

## 같은 티켓이 계속 죽는다

**원인**: `reap`은 같은 이유로 죽는 티켓이 세션을 무한히 태우지 않게 자동 회수를
2회까지만 한다. 3회째부터는 회수 대신 **답변 요청으로 전환**한다 — 티켓 본문에
`## 질문 n`을 붙이고 존재하지 않는 해시를 `deps`로 걸어 다시 열림으로 되돌린다
(자세한 동작은 [도는 세션에 말 걸기](/docs/barge-in) §에이전트가 스스로 잠근다 참고).

```bash
grep -A2 '^attempts' <티켓파일>      # 몇 번째 시도인지
tail -20 <루트>/workers/runner.log | grep ASK
```

`## 질문` 절이 붙어 있으면 사람이 답할 차례다 — 답변 파일이 생기기 전에는 어떤
워커도 그 티켓을 다시 집지 않는다.

## 두 워커가 같은 티켓을 문다

**원인**: 일어나지 않는다. 잡기는 `os.link`로 `<hash>.wip.md`를 만드는 원자적 연산이고,
목적지가 이미 있으면 커널이 `EEXIST`를 줘서 한쪽만 이긴다(판정과 획득이 한 시스템콜
안에 있다). 그렇게 보인다면 실제로 두 세션이 아니라 **워커 락**을 잘못 읽은 것이다 —
같은 워커가 앞 tick의 세션을 아직 쥔 채로 다음 tick이 오면 `SKIP`으로 넘어갈 뿐,
다른 워커가 물었을 수는 있다(동시성 = 워커 개수, [동시성](/docs/concurrency) 참고).

```bash
grep -E 'SKIP|DISPATCH' <루트>/workers/runner.log | grep <해시>
```

같은 해시로 `DISPATCH`가 두 번 이상 찍혔다면 그건 재시도(`reap` 회수 뒤 재디스패치)이지
동시 점유가 아니다 — 시각과 `sid=`를 비교하면 갈린다.
