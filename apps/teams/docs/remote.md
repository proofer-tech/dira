# 원격 큐

> 2026-10-11 현재 원격 큐(`remote.py`와 `dira remote` 명령)는 구현 중입니다. 명령을 찾지 못한다는
> 오류가 나면 아직 설치본에 들어오지 않은 것입니다. 이 장은 완성된 동작을 기준으로 씁니다.

웹 서비스에서 누른 작업을 내 컴퓨터의 dira가 받아서 돌립니다. 서버는 작업을 만들어 나눠 주기만
하고 모델을 돌리지 않습니다. 세션은 이 컴퓨터에서 돌고, 결과물과 온톨로지 원본도 이 컴퓨터의
큐에 남습니다.

연결은 프로젝트 하나 단위입니다. 연결하지 않은 프로젝트는 지금과 똑같이 돕니다. 큐 루트에
`remote.json`이 없으면 원격 동작은 아무것도 하지 않고 끝납니다.

## 연결하기

터미널에서 연결할 프로젝트의 큐 루트를 지정해 실행합니다. `<server>`는 웹 서비스가 알려 주는
주소입니다.

```sh
dira remote connect <server> --root ~/Projects/myproject/.dira
```

1. 명령이 확인 코드(`user_code`)와 주소(`verification_uri`)를 찍습니다.
2. 브라우저에서 그 주소를 열고 확인 코드를 넣어 승인합니다. 승인한 워크스페이스에 이 컴퓨터가
   붙습니다.
3. 명령은 그동안 서버에 승인 여부를 계속 묻다가, 승인되면 나머지를 알아서 합니다. 코드의 유효
   시간이 지나면 rc 1로 끝나니 처음부터 다시 실행하세요.

승인된 뒤 명령이 하는 일은 넷입니다.

- 자격 증명을 `~/.config/dira/remote/<workspace_id>/credentials.json`(권한 `0600`)에, 연결
  설정을 큐 루트의 `remote.json`에 씁니다.
- 이 컴퓨터를 런타임으로 등록합니다. 런타임은 컴퓨터 하나와 AI 도구 하나의 짝입니다.
  `~/.config/dira/bin/engines/`에 있는 도구(`claude` `codex` `agy` `grok`)마다 따로 잡히고,
  로그인을 한 번 점검합니다.
- 그 큐에 워커가 없으면 `workers/w1.sh`를 만들고 [crontab 두 줄](/docs/cron)을 넣습니다.
- 마지막에 안내 두 줄을 찍습니다. 전체 디스크 접근 권한을 주는 것, 그리고 `claude setup-token`으로
  장기 토큰을 받는 것입니다. cron이 띄운 세션은 이 둘이 없으면 돌지 못합니다. 자세한 절차는
  [인증](/docs/auth)에 있습니다.

프로젝트 하나에는 워크스페이스 하나만 붙습니다. 이미 연결된 프로젝트를 다른 워크스페이스에
연결하면 `이 프로젝트는 이미 다른 워크스페이스에 연결돼 있습니다`로 거절하고 rc 2로 끝납니다.
워크스페이스를 바꾸려면 먼저 끊으세요.

## 끊기

```sh
dira remote disconnect --root ~/Projects/myproject/.dira
```

서버에 해제를 알리고, `remote.json`과 그 워크스페이스의 자격 증명을 지웁니다. crontab 줄은
그대로 둡니다. 워커는 계속 돌지만 이제 로컬 티켓만 처리합니다. 워커까지 멈추려면
[cron](/docs/cron) 장대로 crontab의 두 줄을 지우세요.

## 웹에서 누른 작업이 늦게 시작하는 이유

dira에는 계속 떠 있는 프로세스가 없습니다. cron이 30초마다 워커를 한 번 띄우고, 워커는 티켓을
고르기 직전에 서버와 한 번 주고받습니다. 이것을 sync라고 부릅니다. 웹에서 작업을 누르면 다음
sync 때 이 컴퓨터로 내려오고, 같은 차례에 바로 세션이 시작됩니다. 그래서 길게는 30초쯤
기다립니다.

빈 워커가 없으면 더 기다립니다. 한 번에 받아 오는 작업 수는 그 큐의 빈 워커 수만큼이라, 워커가
모두 다른 티켓을 쥐고 있으면 하나가 끝날 때까지 작업은 서버에 남아 있습니다.

sync 때마다 워커별로 다음 실행 시각과 지금 쥔 티켓을 서버에 알립니다. 웹 화면은 이 값을 받아
작업이 언제 시작될지 보여 줄 수 있습니다.

받아 온 작업은 큐에 보통 티켓으로 생깁니다. frontmatter에 `remote_job: <job_id>`가 붙는 것만
다릅니다. 앱 화면에서 다른 티켓처럼 보이고, 같은 규칙으로 가져가고 끝납니다.

## 무엇이 서버로 가고, 무엇이 안 가나

서버로 가는 것은 아래가 전부입니다.

| 무엇 | 언제 |
|---|---|
| 컴퓨터 이름, 프로젝트, AI 도구 이름-버전-로그인 상태 | 연결할 때와 sync마다 |
| 워커별 다음 실행 시각과 지금 쥔 티켓 해시 | sync마다(살아 있음 신호) |
| 원격 작업의 상태(`running` `awaiting` `done` `failed`) | 바뀌었을 때 |
| 진행 기록 - 단계 이름과 세션이 실행한 셸 명령 | 원격 작업이 도는 동안 |
| 사람에게 묻는 `## 질문 n` 절 | 원격 작업이 답을 기다릴 때 |
| 온톨로지 `objects/`와 `versions/` 아래 `.md` 파일 내용 | 바뀌거나 지워졌을 때 |

진행 기록의 단계는 넷입니다. 파일을 처음 읽었을 때(`read`), 처음 고쳤을 때(`wrote`), 새 티켓을
만들었을 때(`handoff`), 답을 기다리기 시작했을 때(`awaiting`)입니다. 셸 명령은 한 줄에 2,000
바이트에서 자릅니다.

서버로 가지 않는 것:

- **구독 로그인 토큰.** `claude setup-token`으로 받은 토큰은 읽지도 보내지도 않습니다.
- **세션 전문.** 모델이 쓴 글, 도구가 돌려준 결과, 사고 과정은 보내지 않습니다.
- 원격 작업이 아닌 로컬 티켓의 상태와 진행 기록.

서버에서 받는 런타임 토큰은 `~/.config/dira/remote/` 아래에만 둡니다. 큐 루트, 티켓, 로그에는
쓰지 않습니다. 작업마다 따로 받는 작업 토큰도 `~/.config/dira/run/remote-jobs/`에 두었다가 그
작업 세션의 환경변수(`DIRA_REMOTE_URL` `DIRA_REMOTE_TOKEN`)로만 넘기고, 작업이 끝나면 지웁니다.

## 서버에서 받아 오는 것

- **작업.** 위에서 말한 대로 티켓이 됩니다.
- **질문의 답.** `tickets/<질문 티켓 해시>.done.md`로 씁니다. 같은 파일이 이미 있으면 덮지
  않습니다. 로컬에서 사람이 먼저 답한 것으로 봅니다.
- **페르소나 묶음.** 서버가 정한 페르소나를 `personas/<이름>/`에 설치하고, 서버에서 온 것이라는
  표시로 `.remote` 파일을 둡니다. 같은 이름의 내 페르소나가 이미 있으면 덮지 않고 그 이름만
  건너뜁니다.
- **온톨로지 스키마 묶음.** 타입 정의를 `_ontology/` 아래에 더합니다. 같은 경로에 내용이 다른
  파일이 있으면 묶음 전체를 거절합니다.
- **온톨로지 편집.** 웹에서 고친 객체를 `objects/`와 `versions/` 아래에 씁니다. 쓰기 직전에 파일이
  웹이 본 판과 같은지 확인하고, 그사이 이 컴퓨터에서 고쳐졌으면 쓰지 않고 충돌로 알립니다.

페르소나와 스키마 묶음은 10분마다 새 판이 있는지 확인합니다.

## 막혔을 때

원격 동작이 실패해도 워커는 멈추지 않습니다. 로컬 티켓은 그대로 돌고, 워커 로그에
`REMOTE <사유>` 한 줄이 남습니다.

| 로그-상태 | 뜻과 할 일 |
|---|---|
| `REMOTE unauthorized` | 서버가 런타임 토큰을 거절했습니다. sync를 멈춘 상태이니 끊고 다시 연결하세요 |
| 도구가 `needs_check`로 보고됨 | 그 AI 도구의 로그인 점검이 실패했습니다. 그 도구로는 작업을 받지 않습니다. 그 도구에 다시 로그인하세요([인증](/docs/auth)) |
| 티켓 fm에 `remote_revoked: true` | 이 컴퓨터가 오래 응답하지 않아 서버가 작업을 돌려받았습니다. 그 티켓의 상태는 더 올리지 않습니다 |
| `REMOTE persona-skip <이름>` | 같은 이름의 내 페르소나가 있어 서버 페르소나를 설치하지 않았습니다 |

로그인 점검은 연결할 때, 6시간마다, 그리고 그 도구로 돈 세션이 인증 오류로 끝난 직후에 합니다.

다음은 [트러블슈팅](/docs/troubleshooting)입니다.
